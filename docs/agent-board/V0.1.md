# Agent Board V0.1 Scope

## Goal

Make the workflow already proven in real Paseo and Orca projects usable through one shared, human-readable board without changing developers' daily tools.

## Board states

The first human-facing board should support these workflow states:

- READY
- IN PROGRESS
- VERIFYING
- RC
- DECISION REQUIRED
- DONE

Internal rhizome states and attempts may remain richer. The board is a workflow projection for people and agents.

## V0.1 capabilities

### Task intake

- Create and edit a task from the Web Board.
- Create and edit a task from CLI / MCP so Codex, Claude Code, OpenCode, Paseo, Orca, and other tools can add work directly.
- Maintain a simple ordered READY queue.
- Do not add sprint, estimation, deadline, roadmap, or portfolio features.

### Execution

- Claim work through the existing rhizome claim / lease mechanism.
- Show the active developer/executor when available.
- Show harness, model, worktree, branch, and current commit when available.
- Preserve checkpoint and handoff support from rhizome.

### Verification

- A Developer cannot declare the task DONE.
- Delivery enters verification after developer submission.
- Independent Verifier records PASS or changes requested.
- Verification must refer to the delivery being checked.
- RC means changes requested; the task returns for developer correction, then starts a new verification round.
- Reverification uses a new verifier session and should not silently reuse the previous verification context.

### Human decision

- A task may enter DECISION REQUIRED when product, architecture, task definition, acceptance criteria, or another authoritative decision is needed.
- Humans can record a decision from the board.
- Human decisions are auditable.

### Completion

- DONE is reached only after the required verification / decision gates are satisfied.
- The board should show the accepted delivery commit or equivalent immutable delivery reference when available.

## Explicit non-goals

V0.1 does not:

- launch or supervise coding agents;
- replace Paseo, Orca, Codex, Claude Code, or OpenCode;
- provide sprint planning, estimates, due dates, roadmaps, or portfolio management;
- provide a terminal or remote shell;
- target multi-tenant SaaS or enterprise authentication;
- require different vendors or models for Developer and Verifier;
- implement a new task-state backend from scratch when rhizome already provides the needed primitive.

## Initial rhizome fit-gap

Keep and reuse:

- SQLite shared project state
- atomic claim
- leases
- attempts
- checkpoints
- handoff/recovery
- review requests/outcomes
- stale-review protection
- workflow gates
- append-only history
- MCP and CLI

Likely additions:

- writable Web Board
- ordered READY queue
- stable executor identity/session metadata
- worktree metadata
- workflow projection for READY / IN PROGRESS / VERIFYING / RC / DECISION REQUIRED / DONE
- independent-verifier guardrails
- RC return-to-current-developer preference with explicit reassignment allowed
- human decision actions
- clearer commit/delivery display

The implementation should prefer additive changes so upstream rhizome improvements remain easy to consume.
